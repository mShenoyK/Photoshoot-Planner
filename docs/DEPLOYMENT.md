## Diagnosing a failed Render deploy

Use the first actual error in Render's deploy log, not this documentation's deployment-status paragraphs. Set Root Directory to the repository root (leave it blank), since commands use the pnpm workspace and root Prisma schema path. Enter only shell commands in the Build/Pre-Deploy/Start fields, without Markdown headings or `Build:` prefixes. Existing dashboard-created services may need their settings updated manually; editing render.yaml does not necessarily update them.

- **Build / EROFS unlink /usr/bin/pnpm:** do not run `corepack enable`, which tries to replace system shims on Render’s read-only filesystem. Invoke `corepack pnpm` directly as shown above; it uses the repository’s pinned packageManager without installing system links. Update existing dashboard command fields manually and redeploy the latest main commit.
- **Build / Prisma CLI not found:** use the explicit `--prod=false` build command above. Prisma and TypeScript are development dependencies needed during compilation and migration.
- **Prisma engine download failure:** retain TLS verification; inspect the build host's access to binaries.prisma.sh. This cloud sandbox's earlier access failure does not establish a Render failure.
- **Predeploy / P1001, P1013, P1000 or TLS error:** verify the securely bound DATABASE_URL, same-region/private-host reachability, credentials and provider TLS configuration. Do not reset the database or disable certificate verification.
- **Startup / missing production build:** verify Build ran from the repository root and succeeded, then use the migration-first Start command above; worker uses `corepack pnpm worker`. Next listens on Render's PORT and 0.0.0.0.
- **Predeploy unavailable on the free tier:** omit the predeploy hook and use `corepack pnpm db:migrate && corepack pnpm --filter @framecraft/web start`. The build still includes the Prisma CLI via `--prod=false`. On restarts, already-applied migrations are skipped; concurrent migration runners use Prisma’s advisory locking and may need retrying after lock timeouts. This is suitable for the initial small deployment; production at scale should use a dedicated release migration job. Never seed/reset production as a workaround.

A root cause is not confirmed until the failing log and service stage are available. After fixing it, verify the deployed commit and run the actual-target smoke script.

## Prisma client auto-install failure in the pnpm monorepo

If `db:generate` reports `pnpm add @prisma/client@6.19.0 --silent`, Prisma did not resolve its declared client in the expected package context. The schema and client live in `packages/database`; the CLI is now also declared at version 6.19.0 in that workspace. Root generation/migration scripts delegate to that workspace so its local CLI resolves the adjacent client. Generation sets `PRISMA_GENERATE_SKIP_AUTOINSTALL=true`: it must use the frozen installed dependencies instead of changing package manifests during a deploy. A regression test exercises Node’s symlink-preserving resolution of the actual installed CLI/client layout.

The root `engines.node` declares `>=22.12.0 <23` so dashboard deployments can select the supported Node 22 line instead of Render’s default Node 24. If an existing service has an explicit NODE_VERSION override, set it to 22. Keep the existing Corepack Build and migration-first Start commands; deploy the latest main commit with a cleared build cache after this dependency/layout change. This sandbox still cannot download Prisma engines from binaries.prisma.sh; successful client generation and migrations on Render must be checked in that deploy log, not inferred from a local mock build.

## Signup/sign-in on the deployed web service

For `https://photoshoot-planner.onrender.com`, set `WEB_BASE_URL=https://photoshoot-planner.onrender.com` and a random, stable `AUTH_SECRET` of at least 32 characters in Render's secure Environment settings. Generate the secret locally (for example, `openssl rand -hex 32`); do not paste it into chat or source. Keep it unchanged across deployments unless intentionally rotating sessions. DATABASE_URL must also remain configured and startup migrations must succeed.

The app now normalizes configured URLs to their origin, accepting a trailing slash, and uses Render's trusted `RENDER_EXTERNAL_URL` when WEB_BASE_URL is absent. An explicitly configured custom domain remains authoritative. Request headers never choose the trusted origin, and foreign browser origins remain rejected. Production URLs must be HTTPS.

Missing/invalid origin configuration produces APP_ORIGIN_NOT_CONFIGURED (503); a foreign/mismatched request produces ORIGIN_REJECTED (403); a missing/short signing secret produces AUTH_NOT_CONFIGURED (503). Session configuration is checked **before** querying/creating an account, so missing secrets no longer leave a newly registered account behind after a failed response. Incorrect login details still produce AUTH_FAILED (401). If an earlier signup saved an account before session signing failed, configure the environment then sign in with the same email/password rather than repeatedly creating it or resetting the database.

`/api/v1/ready` now checks application origin and session signing as well as PostgreSQL, with safe error codes and no secret values. Existing dashboard-created services must configure AUTH_SECRET manually; the Blueprint's generated secret applies only when provisioned through Render's Blueprint workflow. Save environment changes, deploy the latest main commit, then test registration, sign-out, sign-in and opening the protected dashboard. If it still fails, inspect the exact browser error and matching Render request ID/status; do not assume a database outage from a generic authentication failure.

Production-setting regression tests cover Render proxy origin fallback, configured URL normalization, secure JWT cookies, foreign/spoofed origins, authoritative custom domains, missing signing secrets before any account write, readiness configuration errors and incorrect passwords. These tests mock the user repository; they do not establish a working session against the external database. This workspace's outbound proxy denied the live Render domain during investigation, so live success remains unverified here.

## Reference-led planning and OpenAI vision

For the current free web deployment set `QUEUE_DRIVER=inline` (also the default for PostgreSQL when QUEUE_DRIVER is unset). This runs durable SQL-backed plan/export tasks in the web request, with explicit failure/retry and immutable outputs; no Redis worker is required. Keep DATA_MODE=postgres. Configure bullmq plus a worker for larger/long-running workloads. This is an execution mode, not the development mock datastore. Inline responses may already be SUCCEEDED/FAILED, and the UI loads results immediately. Abandoned queued tasks older than a minute and expired running leases can be resumed with the authenticated retry action; `QUEUE_DRIVER=inline pnpm worker --once` is a trusted CLI recovery option when available.

For genuine photo analysis set these secure Render environment values, then redeploy:

```text
AI_VISION_PROVIDER=openai
AI_VISION_MODEL=gpt-4.1-mini
QUEUE_DRIVER=inline
```

Bind `OPENAI_API_KEY` to your own OpenAI project key in secure settings. Do not paste it into chat or Git. AI_API_KEY is a server-only fallback, but the example placeholder is rejected. Mock remains the default without real-provider selection and is clearly labeled: it does not detect image content, body shape or colors. AI_TEXT_PROVIDER=mock remains the supported deterministic text-planning provider; reviewed vision observations are incorporated into its brief and pose directions. Other paid text/image providers are not implicitly enabled by supplying a vision key.

Private reference uploads still require STORAGE_DRIVER=s3 with endpoint/region/bucket/access key/secret; use a private S3-compatible bucket. A free Render web filesystem is not a durable private image store. Missing storage now returns an actionable STORAGE_NOT_CONFIGURED response. See the storage setup above.

Workflow: save a shoot → add each subject and explicitly grant photo-analysis permission (guardian required for minors) → upload a subject, scene or pose reference → click Analyze reference → correct visible proportions, colors, fit and lighting observations → Confirm and use reference → generate/rebalance the relevant tool. Changing consent invalidates linked photos, so set the analysis purpose before uploading or upload again after a consent change. Reference processing holds the shoot authorization/consent lock, checks current purpose consent before image access, verifies derivative integrity and sends only the sanitized WebP plus limited stated context to the fixed OpenAI endpoint. It never sends storage URLs, credentials, original EXIF or subject names/IDs in the vision request. References are not processed automatically on page load.

The body-shape field is an uncertain visual silhouette/proportion impression, not a measurement, health assessment or inferred personality. Group references are not attributed to individual identities; individual wardrobe fit uses only a one-person SUBJECT_PHOTO. Lighting/filters/cropping can distort colors and proportions. Stated preferences take priority; color avoidance includes basic hex hue families. Every result must be reviewed before affecting a plan. Existing locked looks survive re-review of the same still-consented photo; revoked photo permissions purge cached reviews and remove photo-derived locks from future rebalancing. Previously saved private textual plan versions remain historical records; delete the shoot to remove its history and outputs.

Provider HTTP requests use JSON mode with strict server-side Zod validation, a 25-second HTTP deadline and a bounded review size. Live OpenAI connectivity and model quality have not been verified in this workspace; the adapter is tested with synthetic HTTP responses. Configure provider-side spending controls before broader public use. The current session cannot reach the live Render host because of its network policy.
